# UOS 目标机验收

> **状态：等待实测结果。** 本文件是验收的组织方式；具体操作步骤在 RC1 包内的
> `acceptance/TARGET_ACCEPTANCE.md`（中文、逐步、面向操作者）。

## 为什么必须有这一步

Phase 3 的每一个技术决定，都依赖开发机上无法观察的事实：

| 未知                                             | 为什么只能在目标机上回答               |
| ------------------------------------------------ | -------------------------------------- |
| BusyBox `httpd` 给 `.js` 返回什么 `Content-Type` | 取决于该二进制的编译选项，各发行版不同 |
| BusyBox 是否接受 `-c` 配置文件                   | 同上，属于编译期特性                   |
| `xdg-open` 打开哪个浏览器                        | 取决于该用户的桌面关联设置             |
| 端口 8765 是否空闲                               | 取决于这台机器上跑着什么               |
| `crypto.subtle` 是否可用                         | 取决于浏览器版本与运行来源             |
| 禁用 GPU 合成后的滚动体验                        | 取决于这块 CPU 与这个浏览器            |

在这些问题有答案之前做选择，就是在猜。

## 两个阶段

**Stage A（已完成）** — 在开发机上准备：未改动的 Phase-2 构建、只读探针、两个服务候选、
校验与收集脚本、验收手册与结果表，打成 RC1 包。

**Stage B（未开始）** — 在目标机上执行验收，把结果带回，据此选定服务方案，实现最终启动器与
安装流程，再做一次「最终安装形态」的实测。

**候选方案通过测试，不等于最终安装形态通过测试。** 两者要分别验证。

## 交付给操作者的东西

RC1 包（`civic-work-desk-uos-rc1`）是自包含的：解压、校验、按手册做、回传结果。
不需要源码，不需要开发工具，不需要 sudo，不需要联网。

## 必须回传的内容

1. `civic-work-desk-uos-rc1-results-<时间>.txt`（`collect-results.sh` 生成）；
2. 填好的结果表；
3. 响应头抓取文件；
4. 出现白屏或报错时的浏览器控制台原文。

## 脱敏要求

回传的内容里可以有：系统版本、架构、浏览器版本、工具路径与版本、各项 PASS/FAIL、
以及用**测试数据**产生的现象。

不要包含：浏览器配置目录、Cookie、历史记录、个人文档、真实业务记录、完整的家目录列表。

`collect-results.sh` 只收集它自己知道的那几个文件，但**最终由操作者过目后再发送**。

## 验收判定

RC1 验收通过的标准，是能回答「用哪个服务、用什么方式打开、固定端口是否可用、浏览器能力是否齐备、
性能是否可接受」这五个问题，并且核心业务流程、持久化、备份还原、报表导出都通过。

任何一项失败都不是失败的结束，而是 Stage B 的输入：例如 BusyBox 的 MIME 不被接受，就改用
Python 候选并重测该项。
